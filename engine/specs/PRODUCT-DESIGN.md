# OTKAT product design and reference research policy

OTKAT products may learn from the usability, genre conventions and problem-solving approaches of established software and games. The goal is a familiar, high-quality experience with original implementation and meaningful improvements—not a clone.

## Reference-led development loop

1. Identify the user's job-to-be-done and the product category/genre.
2. Review public feature lists, documentation, release notes, user reviews and public community feedback.
3. Cluster recurring complaints into usability, missing capability, performance, accessibility, pricing and platform gaps.
4. Prioritize improvements by user impact, frequency, feasibility and maintenance cost.
5. Create an original product brief, interaction model and visual language before implementation.
6. Implement independently and test against the user needs, not pixel similarity to a reference.
7. Revisit feedback after release and keep a visible changelog.

## Originality boundaries

- Reuse general ideas, workflows, genre conventions and functional requirements where lawful.
- Create original source code, assets, textures, models, audio, icons, UI compositions, copy, names and branding.
- Do not copy proprietary source, distinctive screen compositions, exact icon sets, protected artwork, character designs, maps, levels, sounds, logos or trade dress.
- Do not imply affiliation, compatibility or endorsement without permission.
- A different implementation language or codebase alone does not make copied expressive material safe. Escalate uncertain licensing questions before release.

## OTKAT additions

Every reference-based product brief must include a section titled "What users still need" and propose useful improvements beyond the baseline. Typical areas: customization, accessibility, offline use, export/import, workflow automation, performance, privacy, cross-device continuity and clearer pricing.

## Feedback quality

Treat reviews as evidence, not absolute truth. Separate repeated, reproducible issues from one-off reports; account for version, platform, region and user skill. Never invent user feedback or claim that a feature is frequently requested without supporting evidence.
